# Pi Visual — durable Codex instructions

These rules apply to **every phase (P00–P17)** and focused repair in this repository. They supplement, but do not replace, the current user's explicit instructions and the approved implementation specification. Keep phase prompts short; do not restate this file in conversations.

## Scope and authoritative sources

- This repository is an independent **Rust/Ratatui/Crossterm frontend** using the **unmodified `pi --mode rpc`** backend, primarily in Kitty on Linux. No Pitago runtime, no Pi core patches or monkeypatching, and no substitute tool-execution shell.
- The repository currently lives under `~/.pi/agent/frontend/pi-visual`. Editing this repository is allowed; **do not interpret that as permission to edit the rest of `~/.pi/agent`**, Pi credentials, installed extensions, user settings, sessions or security policies. Use disposable Pi configuration/session directories for tests; never copy live credentials.
- At the start of phase work, read **the relevant part** of `docs/IMPLEMENTATION-STATUS.md` and `docs/PHASE-ROADMAP.md`; consult the master implementation specification, related ADRs and source/protocol docs **only for the current scope**. Do not reread the full master plan for trivial changes. If a referenced source is absent, inspect what is available and state the gap rather than inventing requirements.
- Precedence for scope changes: **current explicit user decisions**, then accepted project decisions/ADRs, then current implementation-status evidence, then roadmap/master-plan baseline. Preserve historical evidence when a requirement changes.
- **Approved change:** `pi-sandbox` is **not** a production dependency. The revised G1 covers verified `pi-permission-system` interception, **not OS-level sandboxing**. Never claim permission checks provide OS process/network isolation. Do not reintroduce or fork `pi-sandbox` without express approval.

## How to execute a phase

1. Establish the actual working state: inspect `git status --short`, relevant source/tests, current phase status, existing CLI and applicable versions. Preserve existing work; do not regenerate the starter or overwrite newer modules. Identify one bounded vertical slice at a time.
2. For substantial architecture/security changes, ask the configured project-local `astra_advisor` for a **read-only, focused review** before major design decisions, and optionally once after validation. **Do not spawn it for routine fixes** or repeatedly on every compile failure. Its instructions are not an enforced read-only filesystem sandbox. Report when advisor invocation was unavailable or unverified; never fabricate its findings. Sol is the sole implementer.
3. Implement the selected phase's functionality and tests; use the official installed Pi RPC protocol as the authority. Address the first real cause of failures, not only the final `could not compile` summary. Do not skip, weaken or delete tests to produce PASS.
4. Keep all UI-only work **local and model-free**: redraw, replay, scroll, Markdown, focus, widgets, graphics, animation and simulation frames must trigger zero additional provider calls or model-visible UI schemas in default mode. A genuinely user-submitted prompt may use the normal Pi provider. Do not introduce model-facing tools just for presentation.
5. Respect the planned phase boundaries. Do not implement later phases merely to polish a demo. Preserve backend-controlled permissions, honest event-derived tool cards, source-backed status/cost/context, safe terminal escape handling, session correctness, cancellation and clean resource disposal. Chromium/HTML execution stays opt-in and separately isolated; never bypass its sandbox.
6. Update `docs/IMPLEMENTATION-STATUS.md` with the exact work, acceptance evidence, blockers, next slice and any approved deviations. Update relevant compatibility/security/architecture/parity documents only when impacted. Do not mark a phase done merely because a subset of tests passed.
7. **Stop at the requested phase.** Do not start the next phase, uninstall packages, change global config, commit, push, switch branches, publish, download browsers or access real providers without separate authorization. Temporary test files under isolated directories are permitted.

## Build and acceptance rules

For every implementation-phase completion, run from the workspace root, unless a proven environment limitation prevents it:

```bash
cargo fmt --all -- --check
cargo check --workspace --all-targets --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --all-targets --locked
cargo build --workspace --locked
cargo build -p pi-visual --locked
```

- Keep `Cargo.lock` committed once generated by Cargo; use compatible dependency requirements, avoid unnecessary exact version pins and feature bloat. Keep Rust stable and the project's minimum supported version current with an explicit review; do not run concurrent Rustup component updates/builds.
- Use `set -o pipefail` when piping build/test commands to `tee`; record the actual command exit codes. Run relevant opt-in/ignored tests explicitly; distinguish **passed / failed / ignored / not run**. Offline fixture and PTY results do **not** substitute for real Pi, real Kitty, sandbox or browser evidence when required.
- Exercise the phase-specific gate from `docs/PHASE-ROADMAP.md`. Record gate as **PASS, PARTIAL, FAIL, BLOCKED or NOT TESTED** with exact reproducible evidence. A gate cannot be declared PASS from mocks alone if it requires a real integration. Inability to perform human Kitty checks means **PENDING**, not PASS.
- No fabricated benchmarks, counts, screenshots, capabilities or runtime statuses. Synthetic demo events must be marked synthetic. Do not claim a build is working if the executable still fails to link or launch.

State explicitly whether Pi/live configuration was touched. Stop; await the next user's phase request.
