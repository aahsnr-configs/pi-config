- **One app and one Pi-first agent platform:** Coding Mode, ordinary chat, native Cowork Mode and the CLI use the same upstream Pi engine, its authoritative configuration and model/provider handling, skills, extensions, security governance, RPC/PTY bridge and task/event architecture. Do not embed OpenWork/OpenCode as a second agent backend, nor create an IDE-only duplicate Pi permission/sandbox engine.
- **Not one universal sandbox:** A Code-to-Cowork UI switch is not itself a security boundary. Local operations with no untrusted execution may use the baseline Pi configuration; autonomous or adversarial tasks must execute inside **a separately isolated worker**, with least-privilege filesystem/network/credential access. These are profiles **within one common security architecture**, not conflicting IDE-versus-CLI sandboxes.
- **Ordinary Coding baseline:** `@gotgenes/pi-permission-system` governs tool-level decisions; `carderne/pi-sandbox` provides shared Pi-native tool controls and OS-enforced Bubblewrap containment for wrapped shell commands. This is **not** a whole-Pi-process or all-extension sandbox; the UI must not describe it as such.
- **Autonomous Cowork default:** If a Cowork task runs untrusted code or accesses untrusted websites, external systems, a computer-use driver, a browser, an isolated desktop, or high-consequence data, default to a **whole-Pi-worker boundary**, preferably a local NVIDIA OpenShell sandbox. A reviewed, hardened `nono` profile may be supported as an alternative where its actual Linux isolation and socket controls meet the task's threat model. These backends require independent acceptance testing; neither automatically becomes a default just by being installed.
- **No automatic sandbox stacking:** Do not wrap every Pi/IDE task in Pi-sandbox + nono + OpenShell together. Choose an approved backend per session/task, verify enforcement, and make necessary Pi resource compatibility decisions explicit. No silent removal/disabling of security hooks, even inside a strong boundary. No security downgrade merely for convenience.
- **Distinct native-host access:** Controlling a user's real Firefox/Chrome/desktop or signed-in native application is not equivalent to controlling a browser or desktop **inside** a sandbox. Real-host GUI automation is a separate higher-trust bridge with narrowly approved applications/actions and its own security policy, to be designed and approved later; no global X11/Wayland/D-Bus/SSH-agent/docker socket bypass.
- **Token optimization by construction:** All local UI, deterministic policy selection, security enforcement, panel navigation, state inspection and policy/status views make zero additional model calls. Stronger isolation itself does not consume LLM tokens; transferring context, invoking computer-use reasoning, running subagents and paid hosted tools may. Preserve model accountability and compare successful tasks empirically.

**Binding principle:** A common security *policy authority* does not imply a shared kernel/process sandbox. Isolation is determined by the capabilities being exercised and the trust of inputs, not solely by which GUI tab is open.

## A. Evidence and architectural precedent

### A1. What is known about ChatGPT's Chat and Work execution

Public OpenAI documentation supports **one product surface with multiple separately governed execution environments**, not proof that chat and every Work task share one identical OS sandbox:

1. Chat remains available even where a workspace disables Work; its mere presence does not itself authorize local shell/desktop access.
2. **Work Cloud** may use cloud computers and a separate cloud browser, with its own cookies/session rather than automatically reusing the user's personal browser.
3. **Work Local** uses controls on a connected local machine, and local filesystem/browser/native-app access has distinct permissions. Connected local work and cloud work can be managed by different requirements; restrictions in one do not automatically secure the other.
4. Local Work sync can coordinate work through the cloud; it does not establish that model input, screenshots and results remain only on the device. An offline connected computer does not grant its resources to the cloud worker.

This is evidence about documented **security/environment boundaries**. OpenAI does not publish enough detail here to assert that all ordinary ChatGPT conversations and all Work modes are inside the *same* sandbox binary or kernel boundary. Do **not** claim insider knowledge of ChatGPT's private implementation.

The lesson for our IDE: **share the conversation shell, governance and task artifacts; segment authority and isolation by actual work.** This is a design inference, not a claim of exact implementation parity with OpenAI.

### A2. What Pi and sandbox vendors substantiate

- Pi extensions execute inside the Pi process with its OS permissions. Tool-intercepting extensions cannot confine arbitrary code that already executes inside an unrestricted Pi process. Pi's own docs recommend isolating the whole Pi process when protection from extension behavior is required.
- `carderne/pi-sandbox` uses Linux Bubblewrap for wrapped Bash commands; read/write/edit Pi tool access is policy-intercepted in-process. Its `denyRead` has approval override semantics and is not an immutable kernel secret boundary. Its documentation warns that broad browser/socket allowances create security holes.
- `@gotgenes/pi-permission-system` provides deterministic allow/ask/deny and agent/MCP/skill gates, **not** an OS sandbox or a compulsory model judge.
- `nono` can contain a launched Pi process with Linux security primitives and supports optional credential proxying, but documented Linux socket/namespace gaps and host-kernel limitations require explicit configuration and verification; do not pronounce it VM-equivalent.
- OpenShell offers full-Pi-process worker isolation with filesystem, process, network and credential controls via a policy-controlled sandbox, but it requires a gateway/container infrastructure. It is not, by itself, a browser or graphical desktop. An isolated browser/desktop must be separately supplied **inside** its worker boundary.
- OpenWork's shared-engine/headless-session architecture is relevant to avoiding duplicate runtime logic, not proof that it automatically consumes fewer tokens. Its docs explicitly say model-backed skills consume tokens and repeated tasks have no automatic result cache.

### A3. Threat model and assets

Protect the user's host/home, Pi and IDE configuration, model/provider credentials, Git metadata and secrets, unrelated projects, authenticated browser sessions, external app accounts, network/private services, approvals, persistent tasks, and session records against: prompt-injected files/pages/MCP responses; untrusted scripts/dependencies; compromised executable extensions; mistaken actions by a legitimate model; excessive autonomous permissions; credential and data exfiltration; GUI/socket escape; permission forwarding errors; context leakage across sessions; and unsafe replay of side effects. Stronger isolation reduces some impacts but cannot prevent all incorrect decisions or an action the user deliberately authorized within the sandbox.

## B. What token efficiency does — and does not — mean

### Hard invariants

**T01. Zero-LLM GUI path.** Opening, closing or rearranging Code/Cowork panels; navigating task cards; filtering/sorting/indexing local task metadata; showing permissions, sandbox policies, resource stats, progress or logs; browsing cached artifacts; local file previews; applying deterministic UI transforms; and switching views within the same Pi session must issue **zero model requests** and inject **zero new prompt/context**. Background UI refreshes use existing events or local storage, not LLM polling.

**T02. Single agent decision loop.** Do not implement an invisible secondary planning/reviewing/chat agent solely to operate Cowork. If the user starts a model-backed task, that is an explicit Pi run with visible selected model, invocation count and usage. The already-approved managed Orchestrator remains a distinct, explicitly governed workflow, not the implicit default for every Cowork action.

**T03. Local-first deterministic execution.** Prefer local programmatic operations where AI judgment is unnecessary and authority is already granted: file listing, metadata filtering, batch renames with a dry-run, exact-text search, local indexing, conversion through installed deterministic tools, sorting, archive extraction, existing-file preview, validation, checksum/duplicate detection and application of *already approved* operations. These local operations need no LLM; they still require filesystem/permission checks and clear previews where side effects occur. Do not pretend complex user goals can always be fulfilled without inference.

**T04. On-demand resources only.** Honor D43: MCP servers stay disabled until explicitly approved for an operation/session, with no `mcp.json` mutation. Reuse existing Pi skills, prompt templates and local command definitions. Limit exposed tools and skill descriptions to the legitimate scope where verified safe, but never hide security hooks or silently alter permission enforcement. Skill descriptions/tool schemas and injected system messages themselves can consume prompt tokens; measure them.

**T05. Minimal task context.** Retrieve exact relevant files/sections/chunks, not broad folder dumps; prefer verified file hashes and source references. Enforce D11 per-task context preview/approval, D42 source provenance and no automatic cross-project knowledge injection. Avoid attaching screenshots, large logs, full documents or broad prior transcripts when a small verified excerpt is sufficient.

**T06. Compact tool results.** Use bounded, structured results with links to full local artifacts. Preserve detailed outputs on disk for inspection, but do not repeatedly paste them into model context. Errors and test failures must retain enough evidence to diagnose rather than be silently truncated.

**T07. Reuse verified outputs.** Cache *local deterministic derivations* and reusable completed artifacts by content hash, software/tool version, task parameters, permissions, model/config provenance and input freshness; reuse only when safe and semantically equivalent. Explicitly distinguish (a) local result cache, (b) provider prompt/cache-read discounts, (c) real model response caching and (d) session reuse. Never assume a model answer is reusable solely because prompt text matches. Never reuse a side-effecting result as proof an external action occurred again.

**T08. No duplicate action on retries.** Track external side effects through receipts/idempotency metadata where supported. Before retrying a failed step, inspect whether it partially completed; request approval for unsafe replay. Retrying a model request can consume additional tokens, and retrying an external operation can repeat its effects.

**T09. Computer-use observation efficiency.** For screenshot/action loops, use the smallest authorized observation that preserves needed detail; crop/downscale or diff only where correct and supported by the chosen computer-use interface. Prefer semantic browser accessibility/DOM observations for supported tasks where permitted rather than endless screenshots; allow a visual fallback when necessary. **Do not** claim that image-processing optimizations always reduce model billable tokens. A provider's hosted computer-use tool can incur **per-tool-call fees** in addition to tokens.

**T10. Distinguish session reuse from context bloat.** View switching must be free; carrying excessive session history into unrelated tasks is not. Offer clear choices to continue, branch or start a fresh context with explicit, cost-visible context transfer. Do not silently ask the model to summarize an old session when opening Cowork.

**T11. Approval-gated model selection.** Use the actual Pi provider/model availability and D07/D47's explicit approval before switching models or reasoning effort. GPT-6.1 Terra (`gpt-6.1-terra`) may be recommended for suitable supported computer-use tasks, never selected silently. Check actual integration support, authentication, billing and tool calling through the supported API. ChatGPT/Codex subscription access does **not** imply unrestricted free third-party API access.

**T12. Bounded delegation.** Subagents may improve task completion but create additional model calls and context. Use existing manually approved managed Orchestrator policies, and require later Cowork-specific approval before introducing autonomous multi-agent delegation or parallelism. Default to one session/agent for simple tasks. Attribute child usage to the parent task.

**T13. Usage/fee observability.** Record authoritative, provider-reported input/output, cached input/write tokens, context usage, model, reasoning, paid tool-call fees where available, nested tool/subagent costs, actual retries and compaction usage. Expose estimates clearly labeled when billing data is unavailable. Provide preflight estimated budgets, per-task cap alerts and an explicit policy for what happens at limits. No artificial zero-cost claims for remote inference or tool calls.

**T14. Verified savings, not marketing.** Establish representative baseline tasks (document transformation, filesystem task, research, browser task, multi-step task, coding task); run A/B comparisons using the *same model, inputs, capabilities, success criteria and security profile*; report cost/tokens per **correctly completed** task, number of model requests, tool calls, latency, context length and failures. Do not claim fewer tokens without measurement and do not trade away safety or fidelity to improve numbers.

**T15. Local security controls stay local.** Permission checks, sandbox setup, policy views, local audit, approval and deterministic workflows invoke no LLM. `@gotgenes/pi-permission-system` model-judge / `authorizerChain` stays empty unless explicitly approved. There is no model-based security supervisor in the background by default.

### Important limitation from OpenWork research

The source reviewed is **`different-ai/openwork`**, an OpenCode-powered Cowork-style desktop app, not a Pi runtime. Its documentation describes headless threads as ordinary OpenWork/OpenCode sessions with the **same** session ID and events, not a new chat engine. Its `what-uses-tokens` documentation explicitly says **there is no task-result cache today** and running skills/sending prompts consumes tokens. Its architecture is useful as a *shared-runtime pattern*, **not evidence of proven lower token use than Pi**. Claude Cowork likewise states that multi-step tasks use additional model tokens. Therefore the requirements above are design targets to implement and benchmark, not inherited performance claims.

## C. Unified security-control plane and execution backends

### C1. Responsibilities must be explicit

| Component | Single owner / contract | Important limitation |
|---|---|---|
| Pi runtime | Agent execution, built-in tools, custom extensions, model/provider configuration, Pi sessions and event data | Not an inherent sandbox or complete permission OS boundary |
| `@gotgenes/pi-permission-system` | Authoritative deterministic Pi tool/MCP/skill/path/agent allow/ask/deny gates | Host hooks cannot constrain an already compromised in-process extension; no kernel sandbox |
| `carderne/pi-sandbox` | Ordinary Pi-native sandbox profile shared by CLI, Kitty and IDE; Bubblewrap-wrapped shell/network constraints and direct tool interception | Bash subprocess containment; *not* all of Pi/extension code |
| IDE security/control plane | Local profile selection, policy evidence, trust/config preview, effective-boundary validation, approval UX, lifecycle/status and audit display | May not invent another competing Pi tool-level policy or override lower-layer denies |
| NVIDIA OpenShell (preferred strong backend) | Separate complete Pi worker within filesystem, network, process and credential boundary, including its loaded extensions | Requires gateway and controlled file/credential transfer; must be tested on Linux |
| `nono` (optional alternative) | Locally wrapped full Pi worker, kernel restrictions, possible credential proxying, audits | Effective socket/namespace/network protection depends on config and kernel; not interchangeable without tests |
| Cowork browser/desktop runner | Task-scoped browser profile or virtual desktop *inside* the selected isolated worker, with authenticated viewing/takeover | Never automatically connects to host display, browser, clipboard or signed-in app |
| Host application bridge (future decision) | Narrow, individually approved actions on real host applications; auditable grants | Distinct, more privileged boundary; not implied by Cowork selection |
| IDE renderer and artifact sandbox | Webview/preview/content rendering under existing D04/D20 security requirements | Separate UI-content containment is legitimate and is not a second Pi agent sandbox |

### C2. Authoritative configuration, consistent entry points

1. Preserve Pi's existing user/project resource roots and custom paths (`PI_CODING_AGENT_DIR`, native package declarations, `sandbox.json`, trusted project overlays) as source of truth; use verified, read-only inspection and user-approved edits. The IDE should not create a private forked copy that drifts from the CLI.
2. Standalone `pi` in Kitty and IDE RPC/PTY use identical **baseline** policy and `pi-sandbox` behavior for equivalent project/session inputs. If a stronger execution profile is selected, a **CLI-accessible launcher** must be available too, with the same profile and effective security verification. A wrapper does not transparently change an unrelated direct invocation of `pi`.
3. Maintain one common security profile catalog and ownership model, with backend-specific adapters translating a reviewed profile into *enforceable* permissions. Report unsupported policy items; do not silently approximate an OpenShell rule with weaker `pi-sandbox` hook checks or vice versa.
4. Preserve native Pi trust decisions and permission dialogs. IDE approvals must resolve actual Pi service requests, not create parallel UI-only approvals. All errors, incomplete propagation or missing security hooks fail closed for protected work.
5. Verify loaded runtime/version, physical backend, security hooks, namespace/kernel capability, mounts, network egress, authorized credentials, parent/child process state and configuration digest before each protected worker launches. Report **effective** containment, not just the intended profile name.
6. For direct Pi CLI execution, show baseline protection truthfully; a regular `pi` invocation is not secretly inside OpenShell. Both CLI and IDE can explicitly start the same higher-assurance profile, but they need not share a Pi process.

### C3. Higher-assurance Cowork must not silently piggyback on a weak Pi process

For a task requiring a stronger process boundary, launch a **new isolated Pi worker** as a deliberately selected execution environment. This still uses the same Pi implementation and compatible extensions/resources, *not* a second agent platform. Reusing an existing host Pi process through a different GUI tab does **not** retroactively sandbox it. The UI must distinguish:

- **In-place view change:** same session identity, risk profile and sandbox; zero LLM calls and context injections.
- **Task in a new strong worker:** independent Pi process/session, compartmentalized files/credentials, explicit minimal context transfer after approval; new turns and possible model/tool charges are transparent.
- **Returning a result:** copy only verified authorized artifacts and concise receipts back into the shared workspace; don't smuggle full untrusted logs, browser cookies or hidden prompts across the boundary.

OpenShell should be the preferred strong backend for an autonomous Cowork task where isolation is mandatory. `nono` can be chosen by an explicit locally verified profile that meets the same test cases. `pi-sandbox` inside a strong worker may remain loaded for tool-level UX **only when compatibility and effective enforcement have been demonstrated**; alternatively a vetted worker profile may intentionally omit its shell wrapper if the stronger boundary already enforces the relevant properties and a no-downgrade review confirms equivalence. **No silent disable, duplicate nested sandbox, lost permissions or deceptive badge.** The implementation must not silently rewrite global CLI `settings.json` merely to change the isolated worker's package set.

### C4. Trust, credentials, network and GUI interfaces

- **Credential protection:** raw `auth.json`, OAuth tokens, SSH/GPG credentials, browser profiles and cloud secrets should not be copied/mounted into an untrusted worker. Prefer reviewed host-side credential routing/proxying with scoped short-lived grants where supported. Not all Pi provider/OAuth flows will work with such routing: verify each provider and fail closed rather than exposing raw credentials as a blanket workaround.
- **Network:** deny-by-default egress for strong workers, allow only approved destinations and methods where enforceable. Deny loopback/private services, DNS/UDP escape, Docker/user service sockets, and undocumented proxy bypasses where supported; test actual enforcement. For an explicit network exception, require scoped approval and disclose whether the worker must be restarted/recreated.
- **Files:** only approved work folders mounted read-only or read-write as required. Untrusted downloads and attachments enter a quarantine/staging area. No implicit mounting of home directory, Pi configuration/auth, IDE extension storage or other projects. Git metadata and `.pi` need separate immutable policy when task should not alter them.
- **Browser/desktop:** browser profile, cookie jar and desktop screen are isolated per workspace/task or another expressly approved sharing scope. Display channels, VNC/WebSocket endpoints and takeover credentials are authenticated, bound to the correct task, expired/revoked appropriately and not globally reachable. Never pass host X11/Wayland, D-Bus, Docker, SSH-agent, arbitrary `/run/user` sockets or CDP endpoints into an untrusted worker for convenience.
- **Application connectors:** API-based connected applications use independent OAuth/resource scopes and audit; their approved access can still have side effects outside a kernel sandbox. Require explicit service/action approvals, provenance and expiration. A sandbox is not a substitute for safe SaaS account permissions.
- **Host computer use:** operating a real desktop/browser is necessarily more privileged than interacting with an isolated virtual desktop. Future native-host bridge must have explicit per-app/per-session scopes, screen/capture boundaries, foreground/takeover/stop controls and consequential-action approvals, and must never claim whole-host containment. No host control is authorized by this D50 proposal.

## D. Risk-based execution policy for chat, coding and Cowork

**Default rule:** Select the least capable approved execution environment that meets the task's requirements **without sacrificing a required security boundary**. Profile selection is deterministic based on explicit task capabilities and user-approved scope, not an invisible model-security judge. When uncertain about elevated access, refuse automatic escalation and request user approval. A hidden model cannot switch profiles or widen a sandbox.

| Profile | Example activity | Mandatory boundary | Default authority |
|---|---|---|---|
| **R0 — View/chat only** | Chat, read-only task list, local preview/inspection, status | Existing IDE renderer and file-view protections; no autonomous execution enabled by opening a view | No automatic Pi tools, GUI host control or extra model calls |
| **R1 — Standard coding** | Existing interactive Pi coding, tests, approved local edits | Shared `pi-permission-system` + `pi-sandbox` baseline, verifying its actual Bash-only OS containment | User-approved workspace/tool/network policy; honest visibility of in-process exposure |
| **R2 — Scoped deterministic Cowork** | User-approved local file transform, rename dry-run, exact search, sorting, cataloging without model reasoning | Least-privilege local deterministic executor under the applicable existing policy; strengthen when handling untrusted executables, external data or sensitive resources | Explicit folder scope; no LLM unless task genuinely needs one |
| **R3 — Autonomous/externally connected Cowork (recommended default for agentic tasks)** | Multi-step unattended tasks, untrusted documents/scripts, browsing websites, web research with execution, browser automation, isolated desktop computer use, unknown extensions | **Full Pi-worker isolation**: preferably OpenShell; verified `nono` alternative; task-scoped browser/desktop runs *inside* boundary | Minimal mounted files, controlled credentials, explicit egress, no host sockets, bounded actions and approvals |
| **R4 — Explicit host computer use** | Control of an existing host browser, native app or signed-in desktop | Isolated agent reasoning plus a distinct narrowly scoped host-action broker; separate policies and approvals | **Not approved by D50**: must await a later Cowork feature/host-access decision |

**Mandatory escalation triggers for R3 or stronger:** executable downloads/build scripts from unknown sources, untrusted browser pages with action tools, headless autonomous runs involving external resources, direct computer-use drivers, untrusted Pi extensions or tools, private/sensitive data with external connections, requests to run code that cannot be safely policy-gated at the ordinary tool layer. The system must not silently fall back from R3 to R1 merely because OpenShell is unavailable. If R3 cannot launch, clearly block or offer an explicitly approved safer non-executing alternative; don't claim R1 is equivalent.

**Risk ≠ mode label:** Merely opening Cowork doesn't start an isolated worker or make an LLM call. A low-risk deterministic task can use R2. Conversely, a Code-mode task using untrusted executable content may require R3. Users can approve a stricter profile at any time; relaxing a non-negotiable safety property must not be accepted without a separate risk and authority review.

**No magical privilege transfer:** Dynamic edits of the OpenShell network policy do not imply runtime changes to static mounts, Landlock or process identity; recreate the worker where a change is static. Likewise, a `pi-sandbox` prompt cannot override the kernel restriction of an outer worker. Deny unsupported mixed-permission requests rather than automatically launching a host process.

## E. Cowork / computer-use security foundation — feature depth decided later

1. **First-class native Cowork, same Pi-first engine.** Tasks, plans, progress, receipts, approvals, file artifacts and conversation views are IDE surfaces driven by Pi events and local state. No second hidden AI agent or model calls to refresh UI, route safety decisions or paint progress. OpenWork-style headless control may be a separate controller, never a second engine. A full-process Cowork worker is still Pi.
2. **Isolated screen by default for agentic computer use.** Provide a separately installed/configured browser and, when approved, a task-contained virtual desktop with authenticated observation and takeover channels. OpenShell alone does not deliver screenshot/input GUI capabilities. Avoid full host-desktop exposure; don't reuse a personal browser's tokens/cookies or CDP ports unless a later, explicitly approved native-host-access decision allows a constrained bridge.
3. **Computer-use model compatibility.** OpenAI lists `gpt-6.1-terra` as supporting computer use through the Responses API. That is not proof that the installed Pi version provides the required adapter, or that the user's ChatGPT/Codex subscription confers unlimited API use. Build and test a supported Pi tool/Responses integration, provider authentication and actual billing. D07/D47 model and thinking-level switches remain approval-gated.
4. **Approval-aware actions.** For consequential financial, legal, account, external communications, uploads, destructive or privacy-sensitive actions, obtain task-scoped confirmation at the point of action. Prevent automatic replay after partial failures. Display effective target identity, intended external destination, permissions and work receipt; no model-only approval substitute.
5. **No unintended privilege via screen tool.** Screenshots/vision tools, accessibility-tree/DOM data, clipboard and virtual input stay inside the worker's intended surface. Reject attempts to use screenshots or browser APIs to access local applications/files not approved for the task. A file cannot become authorized simply because a sandboxed browser can display it.
6. **Resumability and background.** D37/D39/D49 still govern optional scheduled/persistent operation. A stopped/expired worker must not silently resume with a broader profile, replay actions or transfer credentials. If tasks move between workers, preserve only explicitly authorized state and record any cost/permission changes.
7. **Future Cowork feature decisions remain separate.** D50 supplies the security floor, not a blanket authorization for autonomous research, local/remote computer control, email sending, calendar modification, system automation, persistent agents or cloud execution.

## F. Migration plan tied to the reconstructed Pi configuration

**Source-grounded archive facts (not proof of current live machine):** `pi-config-reconstructed.zip` contains `agent/settings.json` declaring `npm:pi-permission-modes` and `npm:pi-subagents`; it does *not* declare `pi-sandbox` or `@gotgenes/pi-permission-system` as installed Pi packages. `agent/sandbox.json` already has sandbox enabled with browser-process access false, shell sandboxing on and an empty allowed-domain list; it denies select private paths but those path strings and semantics must be validated against the live agent root and actual installed extension. `agent/workflow/permissions-adapter.ts` imports `pi-permission-modes` from the package tree. The specific live filesystem, loaded extension variants and custom Pi resource paths must be rechecked immediately before migration. Never copy raw authentication paths or user secrets into public design examples.

**Required migration phases:**

1. **Inventory and backup first.** Record the exact executable/version (archive staged Pi 1.5.2), active user/project Pi package declarations, actual `PI_CODING_AGENT_DIR`, loaded extension paths, sandbox config and runtime grants, custom commands, MCP disabled defaults, Orchestrator adapters, workflow/role rules and trust state; preserve rollback, no secret export.
2. **Migrate permission decision semantics.** Replace `pi-permission-modes` with `@gotgenes/pi-permission-system` only after mapping per-mode rules, role-specific `allow/ask/deny`, external paths, directional access, `workflow-boundary` and emergency host override. Its configuration is not a drop-in replacement. No simultaneous engines in production without proven composition.
3. **Install and validate `carderne/pi-sandbox`.** Test its exact release/schema, Linux Bubblewrap and `rg` dependencies, `sandbox.json` read/write/network semantics, override handling and Pi's direct `!` behavior. Correct the real credential-path deny rules; avoid broad browser or Unix-socket allowances in the ordinary global profile.
4. **Refactor hard-coded workflow adapter.** Remove the direct `pi-permission-modes` import, introduce a reviewed adapter for the new Pi permission service, ensure all role agents receive permissions and approvals, preserve D08/D09 and the original orchestrator fail-closed/single-active boundaries.
5. **Subagent compatibility.** Do not infer native compatibility of `nicobailon/pi-subagents` from `@gotgenes/pi-subagents` docs. Verify child process markers, parent approval forwarding, load of permission/sandbox hooks, per-child profile, explicit failure on missing parent/approval service, no role crossover.
6. **Common profile management.** Add CLI-accessible launchers and IDE selectors for the same baseline `pi-sandbox` and selected strong OpenShell/nono worker profile. Do not rewrite global Pi config to toggle per-worker capability. Track Pi binary, installed extension version and effective policy of each worker, and prevent unauthorized silent source drift.
7. **Strong worker provisioning.** For OpenShell, validate local gateway/container backend, workload isolation, credential routing, filesystem mounts, network egress, required Pi resources and no host GUI/socket exposure. For nono, validate actual Landlock/seccomp/namespace/socket capabilities and credential protection; no default equivalence without evidence.
8. **Only then cut over.** Perform negative tests and data-retention verification, back up and deactivate old package, enable new packages through user-approved steps, regression-test both Kitty and IDE, preserve a reversible restoration procedure. This design document does not authorize making those changes.

## G. Acceptance matrix — non-negotiable

1. **No model work for UI/security housekeeping.** Instrument model requests and context injection; opening Cowork, changing tabs, reviewing policy and using local deterministic displays triggers zero model calls. Offline local actions do not leak data or invoke models silently.
2. **Code/CLI policy parity.** On equivalent baseline sessions, direct Pi in Kitty, IDE PTY and Pi RPC resolve the same Pi permission service/config, expected `pi-sandbox` hooks and effective shell policy; no hidden IDE-only sandbox.
3. **Actual boundary inspection.** Prove R1's shell-only OS sandbox, and R3's *whole Pi process* boundary with effective mounts, network, credentials, process restrictions and no untrusted host sockets. Labels must reflect reality.
4. **Fail closed on enforcement loss.** Kill or misconfigure an isolation backend, block needed kernel features or disable a hook; no protected worker silently falls back to direct host Pi or an unrestricted shell.
5. **Read/write/exfiltration negatives.** Test file reads/writes outside approved scope, symlink/path escape, deny-list overrides, Git/.pi/auth files, network/private addresses, Unix sockets, Docker, D-Bus/systemd, SSH agent, Chrome CDP and subagent process inheritance.
6. **Browser and desktop isolation.** Run screenshot/click/type/browse in an isolated virtual display; verify inability to view/control user's real desktop and personal browser cookies, and that viewing/takeover requires authenticated, scoped access with revocation.
7. **Host-control boundary.** Any experimental host bridge denied by default; no accidental escape through Pi extension tools, screenshots, clipboard, socket mounts, browser add-ons or manual mode selection.
8. **Permission propagation and UI parity.** Existing custom Pi extensions, both permission-system/pi-sandbox interceptors, MCP temporary activation, role-specific policies, subagent approvals and IDE-native GUI dialogs must behave correctly. Fail closed on absent adapter/unsafe prompt forwarding.
9. **Avoid incompatible stacking.** Verify strong backends don't silently stack inconsistent network proxies or duplicate prompts; explicit worker package choices, effective permissions and security trade-offs disclosed and tested.
10. **No hidden auto escalation.** Test risk triggers across Code and Cowork. A user can launch deterministic local tasks without R3 if appropriate; an autonomous untrusted browser/code task requires R3 and cannot silently downgrade on backend failure.
11. **Credentials isolated.** Test compromised tool/extensions cannot read raw host Pi credentials via mounted files, env, socket or process inspection. Provider access via proxy is verified, and unsupported OAuth paths fail instead of leaking tokens.
12. **Action approvals and replay.** Test deletion, external messaging, purchases, uploads and account changes with dry runs, human confirmation, idempotency receipt, interrupted retries and audit; no re-execution without safe preconditions.
13. **Cost accounting.** Attribute model request, context, cache, subagent, compaction, screenshot and hosted computer-use tool charges where available. Worker startup is a local cost but could cause context-transfer calls; distinguish these explicitly.
14. **Measure token efficiency without sacrificing results.** For equivalent successful Cowork tasks, compare reference Pi workflows at same model/input/permissions. Report tokens per *verified successful task*, costs, runtime and correctness. No invented savings target.

# D51 — Proposed Option D: Native Knowledge Work and Scientific/Application Cowork Without Browser Automation

**Status:** Proposed D51 option — **NOT APPROVED YET**. D01–D50 remain approved and unchanged. No Pi configuration, software, agents, permissions, files or services have been modified.

## User-requested design boundary

D51 option B (knowledge work plus autonomous browser/online workflows) is **explicitly excluded**. D51 Option D combines the supported parts of former Option A with the independent, non-B parts of former Option C and adds a first-class scientific and professional software-workflow engine. There is **no** "Everything in B" inheritance.

### In-scope functions

1. **Knowledge and file work** (former A): native local document, PDF, spreadsheet, presentation and other supported deliverable creation/editing, local file organization, research/analysis of authorized materials, reusable Pi skills, multi-step task execution, native progress/approval views, local previews, and deliverables. Research here does **not** authorize browser-based research or automated web tasks.
2. **Scientific and specialized application workflows**: target a broad range of locally available, approved scientific/technical/creative/productivity software, including complex multi-application pipelines, not merely PyMOL. Use application-specific skills, scripts, command APIs, extensions, plugins, parameters, specifications and approved file dependencies. Do not assume every application is supported without an adapter and end-to-end verification.
3. **GUI and desktop interaction** (independent part of former C): operate software inside D50-approved isolated graphical desktops when required; prefer native script/CLI/API automation where equivalent, deterministic, reliable and cost-efficient. A separate, narrowly scoped host-app access path must be approved in a future decision before any actual host desktop control is available. No implied control of the user's existing host sessions, screen, clipboard, browsers or credentials.
4. **Application integration and persistence**: persistent task workspaces, cross-application local workflows, scientific/professional software adapters, advanced output/artifact management, session links, reproducibility and review, using the same Pi runtime/provider/configuration as Coding Mode while respecting execution-boundary-specific sessions.
5. **Scientific input retrieval**: a *specific user-authorized scientific application* may fetch a specifically identified scientific dataset from an explicitly permitted scientific source via its native data client or API (e.g., PyMOL `fetch 1HSG`). This is not a grant for general web browsing, general online research, browser downloads, arbitrary websites, online forms, login automation or open-ended online workflows. Apply D50 network restrictions, explicit allowlists and provenance checks. If dataset retrieval is not authorized or unavailable, request a supplied file or use an already approved local copy; do not silently bypass the restriction.
6. **Complexity and verification**: support workflow graphs/DAGs, dependencies, long runs, resumable checkpoints when the app supports them, deterministic local commands, versioned recipes, result validation, scientific units/parameters/provenance, human review, output manifests, error reporting and rollback where technically feasible. Do not claim scientific validity solely because a command ran or an image exists.
7. **Token optimization**: UI-only browsing of tasks, forms, previews, dashboards, logs, local file selections, deterministic script execution and artifact processing must not invoke an LLM. Use model reasoning only when legitimately needed, batch bounded tool results, retrieve targeted context, avoid redundant screenshots/agent turns, reuse verified outputs appropriately and report actual Pi/model token costs. No guaranteed token savings without measured comparable workflows.

### Explicitly OUT of scope (former D51 B)

- Autonomous/general-purpose web browsing, website navigation or search-engine-driven research.
- Browser automation, browser sign-in and authenticated-site workflows, online forms, web transactions or online shopping/booking.
- Generic browser downloads and open-ended online task automation.
- Inheriting option B indirectly through option C's original "Everything in B" phrasing, through connector marketing, or through the label "computer use."
- Any unapproved host-desktop control, real user browser/profile reuse, arbitrary external network access or automatic model/billing/permission escalation.

**Interpretation:** Named scientific data retrieval by an explicitly authorized scientific application's native protocol/API is a narrow exception needed to support the user's PyMOL example; it does not reinstate any general browser capability. Any broader internet-capable action remains prohibited by this D51 decision unless separately amended by the user.

## Illustrative acceptance scenario — PyMOL (NOT run now)

Input: user specifies PDB entry `1HSG` (HIV-1 protease with indinavir ligand `MK1`) and requests exact PyMOL commands plus the resulting 1200 × 900 ray-traced PNG. A prepared PyMOL skill/adapter should:

1. Verify the requested PDB/ligand identifiers and approved scientific-source access; use a user-provided local structure when direct scientific fetch is unavailable or disallowed.
2. Generate a complete, inspectable `.pml` or supported Python/PyMOL script with specific selections for polymer chains, the `MK1` ligand, protein residues within 4 Å, chain coloring, ligand element colors, vicinity lines, residue-name/number labels, solvent removal and camera framing.
3. Execute the script through the actual installed PyMOL (prefer safe documented headless/batch mode where suitable; use an isolated GUI application only when necessary), in an approved D50 worker with the necessary application dependencies and scoped filesystem access.
4. Produce and return the **exact actual script/commands**, the **actually generated** 1200×900 ray-traced PNG, and a session file `.pse` or equivalent when available/desired. Link the results to the task and preserve the approved scientific input provenance, program version, parameters and run log.
5. Verify image dimensions, successful file creation, nonempty selections, correct ligand identification, distance-selection semantics and any disclosed scientific or rendering limitations. Display execution failures rather than manufacturing an image or reporting unexecuted commands as tested.

PyMOL documentation supports batch mode (`-c`), `.pml` scripts, the `fetch` operation, `ray width,height`, and PNG saving; this scenario is technically plausible subject to installation, runtime checks, permissions, input availability and environment.
