# Pi MCP on-demand readiness tests

**Current verdict: no-go for live use.** Pi 1.5.2 calls `before_agent_start` before the agent creates its run signal. The installed extension requires that signal and refuses activation. Test 1 must pass in a real Pi session before the feature can be considered usable. The installed policy is also disabled and denies every server, as intended for the initial deployment.

This checklist covers a parent Pi session using one explicitly selected, approved server and one read-only tool. Run tests 1–10 before enabling that workflow. Test 11 applies if you intend to use interactive approvals. Child sessions and OAuth/provider authentication are outside this release’s supported workflow.

## Test setup

- Use a disposable Pi agent directory selected through `PI_CODING_AGENT_DIR` and a disposable project. Use the same Pi version and extension revision you intend to run. Load the native MCP manager, on-demand extension and the same permission integration as your normal installation. Keep personal credentials and live endpoints out of the fixtures.
- Create a local stdio MCP fixture with a deterministic read-only tool such as `lookup`, a second unapproved tool, and a record of starts and tool calls. Give `lookup` explicit `readOnlyHint: true` and `openWorldHint: false`. Add fixture variants for missing annotations, delayed discovery and an unavailable tool. Count calls from the fixture so a warning or hidden tool cannot be mistaken for enforcement.
- Put the fixture in the test profile’s native `mcp.json` with `enabled: false`. Start with the deny-all policy. For positive tests only, enable the fixture policy, allow the parent role and `lookup`, and use the SHA-256 of `JSON.stringify` of the effective native definition returned by Pi’s loader. Use the same tool exposure mode you intend to use in your Pi profile.
- Record native MCP file hashes before the run and compare after the suite, including trusted project overrides when present. Use `sha256sum` on each existing file. Keep project config contents out of diagnostics until Pi marks the project trusted. Record the Pi version, result and observed evidence for each test.

## Required tests

| # | Test | Procedure and pass condition |
|---|---|---|
| 1 | Real Pi startup and first use | In a clean parent TUI session, run `/mcp-ondemand status`, `policy` and `audit` as subcommands. Expect the native manager and permission integration to be identified, a valid policy, and zero owned registrations. With the approved fixture profile, submit `[use-mcp:fixture] Call lookup for smoke-check.` through the normal user prompt path. Confirm Pi registers one temporary alias and the tool returns the expected value during that same turn. A missing-signal refusal fails this test. A mocked signal cannot satisfy it. |
| 2 | Disabled by default | With the original disabled policy, submit the same directive. Repeat with the policy enabled but the fixture explicitly denied, and again with its rule omitted. Expect zero registrations, starts and calls each time. |
| 3 | Explicit user authorization | With a valid fixture grant, exercise a leading directive and an affirmative request using an exact configured alias, including mixed case. Verify zero registrations for a generic request, a name with an unmatched suffix, a quoted or fenced example, negation, `[no-mcp]`, a directive embedded later in the prompt, transformed input and an extension-originated message. Try a child session and confirm zero inherited grants or starts. |
| 4 | Policy validation and drift | Try a malformed policy, an unknown key, a conflicting alias, a non-parent role, and a missing or wrong definition fingerprint. Change the fixture definition after computing its fingerprint. Each case must fail closed before registration. During a valid run, change the policy or effective definition before the next call and verify that call is blocked and the owned alias withdrawn. |
| 5 | Native config and project trust | Test a trusted project’s full replacement and its exposure-only override with an explicit `enabled: false`. Verify the grant uses the merged definition and its fingerprint. Put a distinguishable fixture override in an untrusted project and verify the global definition alone is used. Test an omitted or true `enabled` in either permitted layer, even when an override would mask an enabled base. Expect refusal. Verify native file hashes are unchanged. |
| 6 | Runtime prerequisites and conflicts | Separately remove the permission integration, substitute the native manager, make the required discovery tool inactive, exceed the server limit, and introduce a conflicting runtime registration or normalized namespace. Expect refusal before fixture startup and preservation of the other registration and tool settings. With an OAuth or provider-auth definition, expect refusal before any connection attempt. |
| 7 | Tool visibility and per-call enforcement | During a valid run, verify `lookup` is discoverable through the selected exposure mode. Verify omitted and denied tools cannot execute even if requested by exact name. Exercise the native indirect call route for the intended exposure mode, such as codemode. Verify denied calls never reach the fixture through that route either. Repeat with missing read-only or closed-world annotations, and attempt a shared MCP resource call during the grant. Expect zero fixture calls for blocked cases. |
| 8 | Existing permission decisions | Repeat the successful `lookup` case with the installed permission integration configured to deny that call. Verify the fixture receives no call, including through the indirect route used in test 7. Restore the permissive test mode and confirm that the positive control still works. Command presence alone does not prove the permission gate works. |
| 9 | Bounded startup and cancellation | Delay discovery past `readyTimeoutMs` or omit the approved tool. Verify setup is bounded and leaves zero owned registrations or callable tools. Abort a separate run during startup, let the fixture respond late, then verify no late grant appears and a fresh request still works. Exercise shutdown while a registration is owned and verify the old alias is gone. |
| 10 | Cleanup and grant isolation | After a successful run settles, check status for zero grants and owned aliases. Try the former tool name in a new prompt without a directive and confirm zero calls. During another active run, send a steer or follow-up and verify that it revokes the prior grant before the next MCP call. Start a new authorized run to confirm cleanup is repeatable. |

## Test 11. Interactive approval

Use a server rule and tool rule set to `ask`. Decline the server prompt and verify zero starts. Approve the server and decline the tool prompt, then verify zero calls. Approve one tool call and verify exactly one invocation. A second call must prompt again. Change policy while the approval dialog is open, then approve and verify the pending call is blocked. Repeat without an interactive approval surface and verify the required approval cannot be obtained.

## Go/no-go

The feature is ready for this workflow when tests 1–10 pass for the intended Pi version and exposure mode, and test 11 passes if you plan to use `ask`. Before first use with your chosen server, review its effective definition and exact tool allowlist, then repeat the first-use and cleanup smoke checks for a single approved read-only call. Context7 and Keenable currently require an unsupported authentication route in this profile. A successful fixture run does not validate either of those definitions.

This file specifies tests. It records no new runtime results.
